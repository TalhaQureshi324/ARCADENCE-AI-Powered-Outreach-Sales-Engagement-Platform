# Phase 15.1 — Comprehensive Repository Audit

**Baseline:** `develop` @ `e1e52f5` (content-identical to `main` @ `4b77a24`, tag `phase-14`)
**Date:** 2026-11-10
**Method:** Four parallel sweeps (architecture, backend, security, frontend) over the full tree, followed by **firsthand verification of every CRITICAL/HIGH finding** against the source before acceptance. No finding below is reported from assertion alone — each carries an exact code reference that was read and confirmed.

---

## 1. Executive summary

The platform's permission model, tenant scoping, SQL parameterization, RLS coverage, JWT verification, OAuth state signing, credential encryption, upload pipeline, and Stripe disabled-state are **solid and verified**. The frontend is unusually honest — zero mock/fake data, real endpoints throughout.

However, the audit **contradicts the previous "sending verified" release claim**: the outbound-send production wiring was never connected. Three confirmed CRITICAL wiring defects mean that, as deployed, campaigns can never send, the worker cannot submit anything, and outbound webhooks never dispatch. All prior send-path evidence was component-level (specs construct their own scheduler/registry); the production `Main` wiring was never exercised. This is precisely the gap Phase 15.1 was chartered to find.

Additionally, 6 confirmed security defects were **fixed in this subphase** with executed tests (§3), and 5 security risks are documented with a remediation plan (§4).

**Verdict:** NOT launch-ready for sending until §2's wiring defects are fixed (they are small, well-scoped fixes — proposed as remediation wave 1). **Safe to proceed to 15.2 (deployment architecture planning)** — nothing in this audit blocks planning, and the staging deployment work in 15.3 will naturally carry the wiring repairs.

## 2. Confirmed CRITICAL defects — production send pipeline is inert

### C1. Campaign send scheduling is never wired
- `apps/api/src/main/scala/com/arcadence/api/Scheduler.scala:47-119` — `Scheduler.enqueueDue` (the only producer of `send_email` jobs) is referenced **only from test specs** (`SchedulerIntegrationSpec`, `ReliabilityLoadSpec`). Neither API `Main` nor worker `Main` calls it; the API has no scheduler loop.
- Bootstrap is also broken: `CampaignRepos.enroll` (apps/api/.../CampaignRepos.scala:620-625) inserts only `(workspace_id, campaign_id, contact_id)` — `next_step_id` / `next_action_at` stay `NULL` (no default, no DB trigger; verified across all migrations). The scheduler's due-query requires `next_step_id is not null` (Scheduler.scala:142), and `next_step_id` is only ever written *after* a first send (SendHandler.scala:490). **Fresh enrollments can therefore never be picked up, even if the loop ran.**
- **Remediation (wave 1):** seed `next_step_id/next_action_at` at enroll (first step of the campaign variant + `now()`), and run `Scheduler.enqueueDue` on a tick in one process (worker is the natural host — it already owns the queue).

### C2. Webhook dispatch loop is dead code
- `apps/api/src/main/scala/com/arcadence/api/Main.scala:343-347` — `val dispatchLoop = webhookDispatcher.loop(30.seconds).compile.drain.background` is created and never consumed; `.background` returns a `Resource` that is never `.use`d. Enqueued deliveries (CrmRoutes.scala:589-598 `deal.created`, ApiKeysRoutes) sit `pending` forever.
- **Remediation (wave 1):** run the dispatcher under `Resource.use` alongside the server, or move it to the worker.

### C3. Worker ships with no provider adapters — every send dead-letters
- `apps/worker/src/main/scala/com/arcadence/worker/Main.scala:39-40` — `val workerRegistry: Option[ProviderRegistry] = None` (the adjacent comment claiming "SMTP/IMAP adapters work regardless" is **wrong**: SendHandler.scala:340-342 resolves the adapter via `registry.flatMap(_.adapter(...))` for *all* providers, falling to `case _` at SendHandler.scala:448-458 → records `rejected / "provider adapter unavailable"` → `JobQueue.Fail`).
- **Remediation (wave 1):** build the registry from env (`ProviderRegistry.build`) exactly as the API does. SMTP/IMAP and OAuth accounts then both work; OAuth sends without client credentials degrade to explicit per-account failures.

### H1. Lease recovery runs only at worker startup
- `apps/worker/.../SendWorker.scala:130-136` — `requeueExpiredLeases` executes once before `Stream.awakeEvery(...)`, contradicting its own doc comment. A crashed worker's claimed jobs stay stranded until *another* worker starts. **Remediation (wave 1):** requeue on every poll tick.

### H2. Reply-triggered cancellation misses `claimed` jobs
- `apps/api/.../ReplyClassifier.scala:180-189` — `cancelPending` cancels only `status='pending'`; a job already claimed (lease up to 300s) still dispatches. Additionally cancellation runs only when inbox sync runs (manual route; no periodic sync in the worker). **Remediation (wave 2):** cancel `pending + claimed` for the enrollment, and add a periodic inbox-sync job.

### H3. Real sends render with NO personalization data
- `apps/api/.../SendHandler.scala:258-269` — the resolver is built with `firstName = None, lastName = None, company = None, ...` and the context query never selects contact fields. Every `{{first_name}}`/`{{company}}` renders empty in *actual* sends while preview/simulate render correctly. **Remediation (wave 1):** select contact fields in the send context query and pass them into `resolverFor`.

### H5. No unsubscribe mechanism in campaign emails
- Send path composes subject/html/text/signature only; grep confirms no List-Unsubscribe header, no one-click URL, no footer link anywhere in `SendHandler`/`Personalization`/`ComposerRoutes`. Opt-out relies solely on reply-keyword classification (ReplyClassifier.scala:51-64). CAN-SPAM/GDPR compliance gap and Gmail/Yahoo bulk-sender requirement. **Remediation (wave 2):** one-click unsubscribe token + `List-Unsubscribe`/`List-Unsubscribe-Post` headers.

### H7. Quota reservations are never released (latent until C1 fixed)
- `quota_reservation` is insert/increment-only (Scheduler.scala:196-205); no decrement on completion/failure/skip, no daily cleanup. Reserve→enqueue→markScheduled are three separate transactions; on enqueue idempotency-duplicate, the consumed reservation is kept and `next_action_at` is not advanced, so the next tick reserves again — pending jobs bleed the account's daily cap. **Remediation (wave 2):** release reservation on terminal outcomes + advance `next_action_at` on duplicate-enqueue.

## 6. Architecture findings

- **Worker depends on the API app module** (`build.sbt:117` `.dependsOn(core, api)`; worker instantiates `ProviderRegistry`, `SendHandler`, `EmailAccountRepos`, `AccountGuard`, `Events`). Core never imports api/worker (clean), but shared send logic should live in core. Remediation (wave 3): promote send execution to `modules/core`.
- **VerificationRoutes implemented but never wired** — frontend verify/suppression calls hit JSON 404s (VerificationRoutes.scala:88 has no reference outside its file; absent from Main.scala:370 route list). **Remediation (wave 1, one line).**
- Render/MIME assembly duplicated between ComposerRoutes preview (ComposerRoutes.scala:374-399) and SendHandler send (SendHandler.scala:258-278) — already drifting (signature rendering differs). Wave 3: single core render function.
- Suppression checks re-implemented ad hoc in 5 places with differing case handling. Wave 3: one core guard.
- No Hikari pooling in either process (documented decision ADR-0018; direct connections per transaction). Acceptable for staging; revisit under load. Worker cadence vars (`WORKER_POLL_SECONDS/BATCH_SIZE/LEASE_SECONDS`) silently fall back on garbage values and are undocumented — wave 3.
- `Main.scala` ad-hoc `sys.env` reads for `AI_TIMEOUT_MS/AI_MAX_RETRIES` crash startup on garbage values (no validation path like ApiConfig). Hardcoded `appOrigin = "http://localhost:3000"` (Main.scala:68, ProviderRegistry.scala:209) — must become env-driven before any non-local deployment (15.2 will spec `APP_ORIGIN`).
- AI agent "discover audience" step unconditionally uses the labeled SandboxProvider in the production route (AiAgentRoutes.scala:303,391) — sandbox-labeled, safe, but a real-provider path gated by env is needed before this feature is production-honest.
- Dead code: `SendWorker.GenericHandler` (SendWorker.scala:26-29, never registered — and dangerous if it ever were); unused `soon` nav flag in web shell.

1. **WorkerQueue timing flake** — reproduced category known from Phase 14.4 (sleep-based spec fails only under full-suite parallel load). See §9 run results.
2. **Unknown-outcome reconciliation** — confirmed gap: `outcome_unknown` actions are held but no reconcile job type exists (`action_type` enum has only `send_email`,`generic_job`; no handler wired). Recommendation from 14.4 stands (Message-ID resolution with age cap).
3. **AI live-model evaluation** — not executable: requires owner GLM balance top-up; gateway code paths verified (timeout, bounded retry, budget check, approval flow, honest unconfigured behavior).
4. **OAuth round-trip** — production round-trip still blocked on owner app verification; state/PKCE/permission re-check verified sound; deployment hazard is the hardcoded localhost origin (§6).
5. **Monitoring** — not provisioned (owner action, documented in OPERATIONS.md).
6. **Backup restoration** — not exercised in hosting (owner action).
7. **Phase 14 findings** — RLS hardening verified complete: all 99 tables RLS-enabled; 12 deny-by-default engine tables confirmed; sole public policy is the intentional founding counter.
8. **Founding 10,000** — implementation verified sound: single transaction, `FOR UPDATE` lock, capacity from program row, `user_id UNIQUE`, idempotent re-claim, email-verification gate. Per-user abuse controlled; per-IP moot behind JWT. Expiry = claim + 12 months.
9. **Free-tier cost limits / anti-abuse** — **plan entitlements are computed but never enforced** (maxMailboxes/maxUsers/monthlySendCap/maxActiveLeads have no enforcement site outside BillingRoutes), no cumulative contact caps (200k rows per import, unlimited imports). Before public free launch: enforce free-tier caps server-side. Also rate-limit weaknesses (§4).
10. **Launch-ready claims** — corrected by this audit: "sending verified" held only at component level; production wiring is inert (§2). The honest status vocabulary from now on: component-tested ≠ production-wired.

## 10. Deployment blockers (prioritized)

1. **[BLOCKER] Send pipeline wiring (C1+C3)** — enroll seeding + scheduler tick + worker registry. Small, well-scoped, testable.
2. **[BLOCKER] Worker lease recovery on tick (H1)** — single-worker staging would strand crashed leases.
3. **[BLOCKER] Personalization data on real sends (H3)** — sends with empty merge fields are customer-facing breakage.
4. **[PRE-LAUNCH BLOCKER] Unsubscribe mechanism (H5)** + free-tier entitlement enforcement (§7.9) before any real outreach.
5. **[NON-BLOCKING] Webhook loop (C2)**, VerificationRoutes wiring, frontend HIGHs (§5) — wave 1/2.

## 11. Recommended remediation plan

- **Wave 1 (send-pipeline correctness — one subphase, e.g. 15.1B or folded into 15.3):** enroll seeding; scheduler tick in worker; `ProviderRegistry.build` in worker; lease recovery per tick; SendHandler contact fields; wire VerificationRoutes; run webhook dispatcher resource. Each item component-tested; one integration spec proving enroll → due → enqueue → worker send with a stub adapter.
- **Wave 2 (compliance + accounting):** unsubscribe headers/endpoint; reply cancellation covering claimed jobs; periodic inbox sync job; quota reservation release; free-tier entitlement enforcement.
- **Wave 3 (structure):** promote send execution to core; shared render; shared suppression guard; APP_ORIGIN env; worker config validation.
- **Wave 4 (frontend batch):** §5 HIGHs + MEDIUMs, prettier-swept, Playwright-verified.
- **Security backlog (§4):** CORS origin restriction + integrations config encryption land naturally in 15.2/15.3 (deployment config); AI data boundary is an owner policy decision.
