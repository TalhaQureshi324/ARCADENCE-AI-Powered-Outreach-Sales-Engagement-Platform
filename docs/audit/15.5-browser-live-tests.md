## 3. Database failure recovery drill (executed 2026-11-11)

```
DB up:       GET /ready -> {"status":"ready","checks":{"process":"ok","database":"ok"}}
DB stopped:  GET /ready -> {"status":"not_ready","checks":{"process":"ok","database":"failed"}}
DB restarted GET /ready -> {"status":"ready","checks":{"process":"ok","database":"ok"}}   (no API restart)
```
Login page (public route) remains reachable while the DB is down — honest degradation, no fake data. Import startup recovery logs `import recovery: 0 interrupted job(s) marked failed` on every boot; interrupted worker claims recover via lease requeue (WorkerQueue spec).

## 5. Defects found and FIXED in product code this phase

**[FIXED] CSV import: any unmapped column broke `Start import` (422).** The import UI sends `""` targets for unmapped headers ("— ignore —"), but `ImportService.start` validated blank targets as unknown custom fields, so every CSV with a left-unmapped column failed with "Unknown target fields: ." (`ImportService.scala`). **Fix:** blank targets are dropped before validation — unmapped columns are ignored, as the UI promises. **Regression test added:** `ImportIntegrationSpec` "start accepts blank mapping targets — unmapped columns are ignored" (8/8 green); verified end-to-end in the browser by `import.spec` (upload with an unmapped `notes` column → Completed → contacts imported).

Also updated (test-side, not product): all 9 initial suite failures root-caused to staleness/races (§1). Two product-level observations remain tracked from 15.1: the founding offer modal's localStorage-only dismissal (server prefs endpoint unused) and the campaigns SPA occasionally settling on the list after in-page actions (cosmetic — activation state persists correctly; flagged for the pre-launch UI pass).
